Technical whitepaper · World Chain

HumanMandate: spending authority bound to a person, not an address

ETHGlobal Lisbon 2026 World Chain mainnet · chain id 480 Unaudited, hackathon-stage
ABSTRACT

HumanMandate is a payment contract whose spending rules are enforced against an anonymous human identifier rather than against a wallet address. It reads World's AgentBook registry from inside the payment path, so any agent wallet a given person operates draws on that person's single budget, and revoking the mandate cuts off every address that person controls — including addresses created afterwards. Routine spending inside the caps requires nobody present; widening the caps requires a fresh liveness attestation whose EIP-712 digest is bound to the specific amount and the specific payee. The system is deployed on World Chain mainnet, with eleven transactions on the live contract covering both the permitted paths and the designed refusals.

1

The problem: authority is attached to the wrong thing

Every payment instrument in common use binds spending authority to a credential. A card number is a credential. A wallet address is a credential. An ERC-20 allowance is a credential-shaped grant: owner → spender, where spender is an address.

The consequence is uniform across all of them. When you cut off the credential, you have cut off the credential — not the party behind it. The card is cancelled; a new card is issued. The allowance is set to zero; the same operator asks for an allowance on a second address, which costs nothing and appears instantly.

This is tolerable when the party behind the credential is slow and reachable by other means. It stops being tolerable when the party is software that can mint a fresh address per task. Concretely: a payer authorises an agent to buy compute up to a daily limit; the agent misbehaves; the payer revokes. Nothing stops the same operator from deploying a second agent wallet under a second key and requesting a second authorisation, because to the contract that wallet is a stranger with a clean record. There is no primitive that says this person's agents may spend up to X per day — only primitives that say this key may spend up to X. The budget was never a budget for a party. It was a budget for a string of twenty bytes.

2

Why existing tools do not close this

Three families of controls exist. All three bind to keys or accounts, and inherit the same failure.

ERC-20 allowances

An allowance is a mapping from owner to spender address to remaining amount. It has no notion of who operates the spender, no rate limit (only a decrementing total), and no notion of a permitted payee — an approved spender may move funds anywhere it likes. Revocation is per-spender, so it is defeated by a new spender.

Session keys and delegated signers

Session keys narrow authority in time and scope, which is a real improvement over an unbounded allowance. But the unit of authority is still a key: issued to a key, bounded for a key, expired for a key. Two session keys held by the same operator are two independent budgets, and the contract cannot tell they are related. Session keys make each grant smaller; they do not make grants aggregate to a party.

Card-issuer controls

Issuer-side controls (per-transaction ceilings, daily limits, merchant restrictions) do aggregate to an account, which is closer to the right shape — but the aggregation happens off-chain, in the issuer's ledger, under the issuer's discretion, against an account identity the issuer maintains. On-chain there has been no equivalent, because there has been nothing to aggregate against: no identifier that is stable across the addresses one party controls and does not itself become a tracking handle.

The missing primitive is an identifier for a party that (a) a contract can read at spend time, (b) is stable across that party's addresses, and (c) is anonymous. World's proof-of-personhood supplies exactly that. What was missing was reading it inside the payment path instead of at a login screen.

3

Design

The registry read

World operates a registry, AgentBook, at 0xA23aB2712eA7BBa896930544C7d6636a96b944dA on World Chain mainnet. It exposes lookupHuman(address) returns (uint256), mapping an agent wallet address to an anonymous human identifier derived from a World ID nullifier.

HumanMandate calls this registry from inside the spend function. Every rule — the caps, the window, the revocation — is evaluated against the identifier returned for msg.sender, not against msg.sender itself. That single relocation is the whole idea: identity moves from the login screen into the payment path, where it can actually gate money.

humanRef: never store the nullifier

The raw human identifier never touches storage, calldata, or logs. The payer authorises a derived reference:

humanRef = keccak256(abi.encode(block.chainid, address(this), humanId))

Because the chain id and the contract address are inside the preimage, the same person has a different reference in every deployment. Nothing that HumanMandate persists can be used as a cross-context handle for a person, and nothing an observer reads off-chain links two deployments together. The contract gets an identity that is stable where it needs to be stable — across that person's addresses, within this contract — and useless everywhere else.

Fail-closed

The registry call is wrapped in try/catch. If the registry is unreachable, refOf returns 0 and every spend reverts. An identity system that fails open is not an identity system; the absence of an answer is treated as the absence of authority.

The rolling window

WINDOW = 1 days, measured as a rolling 24 hours from the first spend of that window — not a UTC calendar bucket. This is deliberate. A calendar bucket permits two full caps to clear seconds apart across midnight, which means a "daily limit" of X is really a limit of 2X over any interval short enough to matter. A rolling window from first spend removes that edge.

Two caps and a fixed payee

  • windowCap — the total that may move within the rolling 24 hours.
  • perTxCap — the ceiling on any single payment, so the whole budget cannot leave in one call.
  • recipient — fixed at authorisation. Funds can only ever reach the payee named when the mandate was created. An agent that goes wrong can spend the budget; it cannot redirect it.

Custody and structure

The contract holds an allowance, not funds. Custody never moves. There is no owner, no pause, and no proxy — nothing in the deployment can reach into a mandate after the fact.

Mandates are keyed mapping(address payer => mapping(bytes32 mandateId => Mandate)), so one payer holds many independent mandates. authorize refuses to overwrite a live mandate and reverts AlreadyActive, because silently re-arming an existing mandate would be an ungated limit raise wearing the costume of a create.

revoke operates on the person. Every agent that person operates loses the mandate in the same transaction, present and future addresses alike — a later address resolves to the same reference, and that reference is no longer authorised.

lowerCap is never gated: tightening your own leash should always be free and instant. Only raiseLimits costs anything.

4

Step-up authentication

The governing principle is asymmetry. Spending inside the limits you already set requires nobody to be present — that is the point of giving an agent a budget. Widening those limits is a different act, and it costs a face.

raiseLimits requires a fresh liveness attestation, signed by a dedicated attestor key over an EIP-712 digest. The digest binds:

account + mandateId + newCap + newRecipient + deadline

This is PSD2 RTS Article 5 dynamic linking applied on-chain. The regulation requires the authentication code to be bound to a specific amount and a specific payee, so a user who authenticates cannot be tricked into authorising a different transfer than the one they saw. The contract enforces the same property: the person's face does not approve "an escalation" in the abstract, it approves this cap to this payee. An attestation captured for one raise is worthless for another.

Digests are single-use — a usedStepUp mapping records consumed digests, so a spent attestation cannot be replayed, including by whoever transported it. The deadline bounds how long an unused attestation stays valid.

The attestor is a dedicated signing key, deliberately separate from the deployer key, at 0x9F05370815CC50Ab913Dc090632841C8cd161d6E. Separating it means that compromising deployment credentials does not by itself yield the power to approve limit raises.

Threat model

Four attackers, stated as what each can and cannot do against a live mandate.

(a) An attacker with a fresh address

Can

Create unlimited addresses at zero cost, and call the contract from any of them.

Cannot

Spend anything. A fresh address has no AgentBook entry, so refOf returns 0 and the call reverts NotHumanBacked. This is the case that defeats allowance-based systems and is closed here (transaction 6 below). If the attacker is the revoked person returning on a brand-new address, the registry resolves that address to the same reference, which is no longer authorised: NotAuthorized (transaction 11).

(b) An attacker holding the agent's key

Can

Spend up to perTxCap per call and up to windowCap per rolling 24 hours — the full budget the payer intended the agent to have. This is not a bug; a compromised agent is indistinguishable from a misbehaving agent, and the caps exist precisely to bound both.

Cannot

Exceed either cap (transactions 7 and 8). Send funds anywhere except the fixed recipient. Raise the limits, which needs an attestation the agent key cannot produce (transaction 9). Survive revocation, which is keyed to the person, so the attacker cannot escape it by moving to another address the same person controls. Worst case is bounded by one window's cap and lands in the payee's account, not the attacker's.

(c) An attacker with the payer's unlocked phone

Can

Authorise new mandates and initiate a limit raise, since they hold the payer's signing capability.

Cannot

Complete a limit raise without producing a liveness attestation over the exact new cap and recipient. Possession of the device is not possession of the face. This is the specific attack dynamic linking is designed for: the payer's own signature is necessary but not sufficient to widen authority.

(d) An attacker holding the attestor key

Can

Forge liveness attestations, and therefore approve limit raises that no live person consented to. This is the sharpest single point of failure in the design and we state it plainly.

Cannot

Move funds on their own. A raise still requires the payer's transaction, so the attestor key alone cannot spend, cannot exceed an existing cap, and cannot redirect funds to a new recipient without the payer also signing. The compromise is serious but it is a two-key attack, not a one-key one. Mitigation is discussed under limitations.

Evidence

The contract is deployed and exercised on World Chain mainnet. Eleven transactions were mined against the same contract, 0x7fcEc100ADc4e89b09a92e3f7931161791D06054.

Five succeed. Six revert — and the six reverts are the point. Each is a designed refusal, mined deliberately so the refusal is verifiable on-chain rather than asserted in a slide. A rule you can only watch succeed is a rule you take on trust; a rule whose refusal is mined with a matching error selector is one anyone can check. The discriminating test: #2 paired with #6

Most of the table demonstrates rules that any contract could implement. Two rows demonstrate that the registry read is doing the work, and they only demonstrate it together.

Transaction 2 shows an address that the mandate never named, and that nobody ever approved, spending successfully. On its own this proves nothing good — it is equally consistent with a contract that simply has no access control.

Transaction 6 shows an address with no human behind it being refused with NotHumanBacked. On its own this also proves nothing interesting — it is consistent with an ordinary allowlist that happens not to contain that address.

Together they are decisive. The contract admits an address it was never told about and refuses another address it was never told about, and the only variable distinguishing them is whether the AgentBook registry resolves them to the authorised person. There is no allowlist, and there is no missing check. The gate is personhood.

Test suite

40 tests pass across four suites: HumanMandate (18), DcaLeash (7), StepUp (11), AgentBookFork (4). The AgentBookFork suite runs against a real World Chain mainnet fork pinned at block 32845385, so the registry integration is tested against the deployed registry rather than a stand-in. Passing tests are not the evidence of record here — the eleven mainnet transactions are. The suite makes that behaviour reproducible; it does not substitute for it.

Platform constraints

Four properties of the World App environment shaped the design. They are stated because they are load-bearing, not incidental.

Approvals do not persist

World App automatically revokes ERC-20 approvals after each transaction (documented on the docs.world.org send-transaction page). The consequence is structural: no standing allowance can exist in a World mini app using plain ERC-20 approvals, and therefore no recurring payment and no agent-initiated payment can exist either. Anything that needs to pay later, without the user present, cannot be built on approvals at all. HumanMandate's on-chain mandate mapping is a way around this — the authority lives in contract state that survives the transaction, rather than in an approval that does not.

Contract allowlisting

Contracts must be allowlisted in the World Developer Portal, or sendTransaction is rejected with invalid_contract. Deployment is not sufficient to be callable from a mini app.

AgentBook requires Orb verification

Only Orb-verified accounts can register an agent; device-level World ID accounts cannot. This raises the assurance of the identifier HumanMandate reads, and it also bounds who can use the system today.

SDK and navigation

MiniKit 2.x removed MiniKit.verify; World ID verification now lives in the separate @worldcoin/idkit package. Separately, World's Quick Actions deep link format is https://world.org/mini-app?app_id={app_id}&path={path}, intended for one mini app to invoke a feature of another. There is no documented mechanism for the invoked app to hand control back to the caller — the platform provides a one-way link only, which constrains any flow that would bounce a user out to another mini app mid-transaction and expect them back.

8

Limitations and future work

Scope of the instrument

The mandate moves one ERC-20 to one fixed payee. It is not a general-purpose consumer card, and there is no merchant network behind it. The fixed payee is a security property, but it is also a limit on what the thing currently is.

Test money

The on-chain demonstrations used a test token ("DemoUSD"), not real money. The contract logic and the registry read are exercised on mainnet; the value moved is not real value.

A single attestor key

Liveness attestations are signed by one key. Compromising it would let an attacker forge step-up approvals. As set out in the threat model, that attacker still cannot exceed an existing cap without an attestation being used, and cannot redirect funds without the payer also signing — but this is the weakest link in the system as built. A production deployment should use a threshold signature or MPC arrangement so that no single key can attest.

Inherited registry assurance

AgentBook's register() has no ownership check, so any Orb-verified user can bind an agent address to their own humanId. HumanMandate inherits whatever assurance AgentBook provides and does not attempt to exceed it. The design decision — read the registry inside the payment path — is orthogonal to how strong the registry is, and improves as the registry improves.

Maturity

The project is hackathon-stage and unaudited. Nothing here should hold real money without review.

Future work

  • Threshold or MPC attestation to remove the single-key dependency.
  • Multiple recipients per mandate, or a payee set, without giving up the property that funds cannot go to an arbitrary address.
  • Multi-asset mandates with per-asset caps.
  • An audit, and a review of the rolling-window accounting under adversarial timestamp conditions.
